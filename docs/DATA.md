# Data: what is in the app, and where it came from

The app ships one bundled historical dataset, `app/src/main/assets/pace_dataset.json`, generated by
`tools/build_dataset.py`. Historical CPI and Surface Speed readings are bundled. The optional
Live now feature does make runtime HTTPS requests to ATP's scores page and Infosys Stats Plus;
it refreshes while the app is open.

## The two series

### 1. Court Pace Index (CPI)

| | |
|---|---|
| Source | courtspeed.com, Court Pace Index database |
| Compiled from | ATP / Tennis TV broadcast data (Hawk-Eye) |
| Metric | CPI points, roughly 18–50, higher is faster |
| Coverage in this app | 106 readings, 14 events, 2012–2026 |
| Events | The four Grand Slams, the nine Masters 1000s and the ATP Finals |
| URL | https://courtspeed.com/ |

What it is: a physical measurement of ball–surface interaction, combining the coefficient of
friction with the coefficient of restitution. Published formula:

```
CPI = 100(1 − μ) + 150(0.81 − e)
```

Limits worth knowing: readings come from the courts where Hawk-Eye is installed, so outer
courts and qualifying are unmeasured; there is no altitude adjustment; and the value rises
through a tournament as the surface grit wears away, so an early-round court is measurably
slower than a final-week one.

### 2. Surface speed

| | |
|---|---|
| Source | Tennis Abstract, ATP Surface Speed Ratings |
| Metric | Ace rate adjusted for the field, 1.00 = tour average, usual range 0.50–1.50 |
| Coverage in this app | 62 readings, 62 events, 2026 season (last update 2026-11-02) |
| URL | https://tennisabstract.com/reports/atp_surface_speed.html |

What it is: for every match, compare the aces actually hit with the aces the same server and
returner would be expected to hit against each other on a neutral surface, then average the
ratios across the event. It is behavioural, so it absorbs temperature, humidity, wind, balls
and altitude along with the surface itself.

Limits worth knowing: it needs matches to have been played, small draws are noisy, and the
year-to-year correlation for a single event is weak (r ≈ 0.35), which is why multi-year
averages are more trustworthy than one edition.

### Live event estimate

While the app is open, the ATP current-scores hub is re-read every five minutes. The app resolves live event routes to its tournament catalogue (ATP 1000, 500 and 250 only), then follows the tournament results page's completed singles stats links. Those links supply the year, event ID and match ID. Match statistics are fetched as JSON from ATP/Infosys Stats Plus using the `/prod/api/stats-plus/v1/keystats/year/{year}/eventId/{eventId}/matchId/{matchId}` endpoint, with the static `/static/prod/stats-plus/{year}/{eventId}/{matchId}/keystats.json` feed as fallback. The encrypted `lastModified`/`response` envelope is AES-CBC decoded, then the app reads both players' ace counts and total service points from the `setStats.set0` whole-match aggregate. If ATP omits `set0` for a match that was played but ended in retirement, the app safely aggregates `Aces` and `Service Points Won` across every non-empty played-set array; it rejects the fallback if any played set lacks either required statistic. A walkover has no played-set arrays and remains excluded. Only archive-route singles links enter the completed-match denominator; live-route links are counted separately and excluded. Doubles links and guessed match-ID ranges are excluded. Each live result also reports the successful/discovered match count and the IDs/reasons for any Stats Plus records that were not usable; cached matches no longer present in the current results page are excluded. For the Paris Masters 2026 45/47 diagnostic, the two confirmed missing IDs are `ms043` (Arthur Rinderknech vs Francisco Cerundolo, retired; 7–5 aces, service points 47/69 and 45/68) and `ms053` (Denis Shapovalov vs Karen Khachanov, retired; 8–2 aces, service points 61/97 and 53/84). Both matches were played and should be included; the Alcaraz–Berrettini walkover remains excluded. ATP Infosys requests retry transient 403/408/425/429 and 5xx responses up to three times with exponential backoff and `Retry-After`; match requests are limited to two concurrent requests. The final HTTP status, server, retry header and short error-body sample are retained for diagnosis. The provisional live figure is:

`(completed-match aces ÷ completed-match service points) ÷ 0.078313`

It is an event-level ace-rate estimate, not the full per-player server/returner adjustment used for the published historical series. The row includes the number of completed matches supporting it. If the results page yields no archived singles links, the app reports the actual rendered-page byte count and stops rather than attempting 96 fabricated IDs.

### 3. Recomputed speed history (2012–2025)

| | |
|---|---|
| Source | ATP match archive compiled by Jeff Sackmann, CC BY-NC-SA 4.0 |
| Mirror used | https://github.com/Aneeshers/tennis-sackmann-archive |
| Metric | Same ace-based scale as above |
| Coverage in this app | 435 readings, 2012–2025 |
| Script | `tools/compute_speed.py` |

Every tour-level main-draw match with serve stats is read. For each player and season the ace
rate is computed on clay and on hard/grass, blended one third to two thirds, and each player's
rate of conceding aces while returning is recorded. For every match, the aces the server would
be expected to hit against that returner on a neutral surface come from the odds-ratio
combination of those two rates; the ratio of actual to expected aces is averaged across the
event, and the season is normalised so a tour-average event reads 1.00.

Validation against the published 2026 season: correlation 0.93 across the 20 overlapping
events, mean absolute difference 0.10. The published reading wins wherever both exist, one
reading at a time rather than season by season, because the published table is a rolling
52-week window that straddles two calendar years.

## Fields in the dataset

```json
{
  "meta": { "generated": "2026-11-03", "season": 2026, "sources": [ ... ] },
  "tournaments": [
    { "id": "madrid", "name": "Madrid Masters", "city": "Madrid", "country": "ESP",
      "surface": "CLAY", "indoor": false, "level": "M1000", "altitudeM": 667 }
  ],
  "readings": [
    { "t": "madrid", "s": 2026, "cpi": 29.8, "src": "courtspeed" },
    { "t": "madrid", "s": 2026, "speed": 0.86, "ace": 8.7, "date": "2026-04-22",
      "src": "tennisabstract" }
  ]
}
```

A tournament may hold more than one reading in a season — one per source — so lookups are by
metric, not just by season. `PaceData.value(id, season, metric)` handles that; the detail
screen merges the rows for display.

## Derived values, and where they are computed

| Value | Where | Definition |
|---|---|---|
| Pace category | `PaceCategory.of` | ITF bands: ≤29 slow, 30–34 medium-slow, 35–39 medium, 40–44 medium-fast, 45+ fast |
| Speed band | `SpeedBand.of` | Our cut points on the ace-based scale: <0.75, <0.92, <1.08, <1.25, above |
| Change vs previous edition | `PaceAnalytics.ranking` | Against the most recent earlier season with a reading, skipping cancelled years |
| Is the move real | `PaceAnalytics.isMeaningful` | ±2.0 CPI points or ±0.05 speed — the ITF quotes ±2 points of uncertainty on its own method |
| Three-year average | `PaceAnalytics.threeYearAverage` | Mean of the readings inside a three-season window |
| Percentile | `PaceAnalytics.percentile` | Position within that season's field for that metric |
| Divergence | `PaceAnalytics.divergences` | CPI percentile minus speed percentile; |gap| ≥ 0.35 counts as a disagreement |

## Known gaps in the underlying data

- 2020 and parts of 2021 were cancelled, so those seasons simply have no readings.
- CPI history for the Grand Slams is thin before 2016.
- Roland Garros has no ace-based speed reading in the current 2026 list.
- Altitude is stored for a few venues only (Madrid 667 m, Gstaad 1050 m, Kitzbühel 762 m).
- The ace-based series is only carried for the current season in this build; the source
  publishes back to 1991 and extending coverage is a matter of adding rows.

## Regenerating

```bash
python3 tools/build_dataset.py
./gradlew :app:testDebugUnitTest
```

The script holds the two source tables verbatim and asserts that every reading points at a
declared tournament. The tests then re-check the generated file: unique ids, no orphan
readings, plausible ranges, no duplicate readings per event and season, and the expected
coverage counts. A typo therefore fails the build rather than showing up as a strange number
on screen.
