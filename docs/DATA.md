# Data: what is in the app, and where it came from

The app ships one bundled historical dataset, `app/src/main/assets/pace_dataset.json`, generated by
`tools/build_dataset.py`. Historical CPI and Surface Speed readings are bundled. The optional
Live now feature does make runtime HTTPS requests to ATP's scores page and Infosys Stats Plus;
it refreshes while the app is open.

## The two series

### 1. Court Pace Index (CPI)

| | |
|---|---|
| Source | courtspeed.com, Court Pace Index database |
| Compiled from | ATP / Tennis TV broadcast data (Hawk-Eye) |
| Metric | CPI points, roughly 18–50, higher is faster |
| Coverage in this app | 106 readings, 14 events, 2012–2026 |
| Events | The four Grand Slams, the nine Masters 1000s and the ATP Finals |
| URL | https://courtspeed.com/ |

What it is: a physical measurement of ball–surface interaction, combining the coefficient of
friction with the coefficient of restitution. Published formula:

```
CPI = 100(1 − μ) + 150(0.81 − e)
```

Limits worth knowing: readings come from the courts where Hawk-Eye is installed, so outer
courts and qualifying are unmeasured; there is no altitude adjustment; and the value rises
through a tournament as the surface grit wears away, so an early-round court is measurably
slower than a final-week one.

### 2. Surface speed

| | |
|---|---|
| Source | Tennis Abstract, ATP Surface Speed Ratings |
| Metric | Ace rate adjusted for the field, 1.00 = tour average, usual range 0.50–1.50 |
| Coverage in this app | 62 published event-season values across 2025–2026 (last update 2026-11-02); 31 are retained as side-by-side references where CALC exists |
| URL | https://tennisabstract.com/reports/atp_surface_speed.html |

What it is: for every match, compare the aces actually hit with the aces the same server and
returner would be expected to hit against each other on a neutral surface, then average the
ratios across the event. It is behavioural, so it absorbs temperature, humidity, wind, balls
and altitude along with the surface itself.

Limits worth knowing: it needs matches to have been played, small draws are noisy, and the
year-to-year correlation for a single event is weak (r ≈ 0.35), which is why multi-year
averages are more trustworthy than one edition.

### Live event estimate

While the app is open, the ATP current-scores hub is re-read every five minutes. The app resolves live event routes to its tournament catalogue (ATP 1000, 500 and 250 only), then follows the tournament results page's singles stats links. Those links supply the year, event ID and match ID. The app inspects each owning ATP match card for generic result markers (walkover/W/O/W.O. and retirement/RET/retired); this is status parsing, not a per-tournament or per-match allowlist. A walkover is excluded before stats lookup and cached as a no-play result. Live-route links are excluded as in-progress. Match statistics are fetched from ATP/Infosys Stats Plus using the versioned API endpoint `/prod/api/stats-plus/v1/keystats/year/{year}/eventId/{eventId}/matchId/{matchId}` first, with the static S3-backed `/static/prod/stats-plus/{year}/{eventId}/{matchId}/keystats.json` feed as fallback. An investigation of a live HTTP 403 found a working Infosys integration that explicitly documents CloudFront/WAF rejection of minimal-header requests. The app now uses HTTP/2 (HTTP/1.1 fallback) and the complete ATP browser header set (`Accept`, `Accept-Language`, `Origin`, `Referer`, `sec-ch-ua*`, and `Sec-Fetch-*`). Transient 403/408/425/429/5xx and network failures retry up to three times with exponential backoff, honour numeric `Retry-After`, and limit concurrent reads. Explicit S3 `AccessDenied`/`NoSuchKey` responses are extracted from the XML body and are not pointlessly retried; the next endpoint is attempted instead. The encrypted `lastModified`/`response` envelope is AES-CBC decoded. For a played match, the app prefers the `setStats.set0` whole-match aggregate; if it is absent or incomplete (common in retirement data), it sums Aces and Service Points Won from every non-empty `set1`–`set5` array, including a partially played final set. It validates non-negative aces, positive service-point totals and `aces <= service points`; it rejects the per-set fallback if any non-empty played set lacks either required stat. Infosys metadata (`matchCompleted`, `isDoubles`, `setsCompleted`, and played-set arrays) is used to distinguish in-progress, doubles, no-play and incomplete records. A retirement with played-set data remains eligible; a confirmed no-play/walkover is excluded and cached; an unrecognised or unavailable stats response remains visible as missing rather than being silently dropped. Only archive-route singles links enter the completed-match candidate set; live links are counted separately and excluded. Each live result reports successfully rated matches, played matches expected, walkovers excluded and missing IDs/reasons. Cached matches no longer present in the current results page are excluded. For the Paris Masters 2026 45/47 diagnostic, the two confirmed missing IDs are `ms043` (Arthur Rinderknech vs Francisco Cerundolo, retired; 7–5 aces, service points 47/69 and 45/68) and `ms053` (Denis Shapovalov vs Karen Khachanov, retired; 8–2 aces, service points 61/97 and 53/84). Both matches were played and should be included; the Alcaraz–Berrettini walkover remains excluded. ATP Infosys requests retry transient 403/408/425/429 and 5xx responses up to three times with exponential backoff and `Retry-After`; match requests are limited to two concurrent requests. The final HTTP status, server, retry header and short error-body sample are retained for diagnosis. The live figure now uses the same opponent-adjusted formula as the historical recomputation. The app downloads the season-wide player profiles and normalisation factor generated by `tools/compute_speed.py` from the ATP match archive. Early in a calendar year, before five events have enough usable adjusted server-side observations, the pipeline uses the previous completed season's profiles and normaliser while tagging the baseline for the current season; this keeps the formula consistent without publishing an unstable early-season normaliser. For each server side it estimates neutral-surface expected aces from that server's season serve rate and the opponent's season ace-concession rate, divides actual aces by expected aces, averages the valid server-side ratios for the event, then divides by the season-wide mean of event raw scores. The player profiles use the historical pipeline's clay versus hard/grass weighting and minimum-sample rules. A minimum of 20 valid server-side observations is required. If a player profile or the matching season baseline is unavailable, that observation is omitted; the app never silently falls back to the old pooled ace-rate formula. The displayed match count still reports every successfully parsed played singles match, including retirements with valid played-set stats; walkovers remain excluded. The live cache is method-versioned so a number produced by the former pooled formula is not reused as if it came from this method. If the results page yields no archived singles links, the app reports the actual rendered-page byte count and stops rather than attempting 96 fabricated IDs.

### 3. Calibrated speed calculations (2012–2026)

For the current season, the pipeline prefers TennisMyLife's current-year ATP CSV because the
Sackmann mirror can lag the live season. Historical seasons continue to use Sackmann. ATP 250/500
numeric tourney levels in the TML CSV are treated as eligible main-tour events; Davis Cup (D) is
not included. The current-year source is refreshed on each pipeline run, and a clearly logged
Sackmann fallback is used only if TML is unreachable and no cached TML file exists.

TennisMyLife's published terms limit its data to personal, educational and non-commercial research;
the project stores derived event ratings and player-profile summaries, not the raw TML match CSV.
No commercial use or raw-data redistribution is authorized by those public terms. Confirm current
terms and obtain written permission before any commercial use or raw-data republication.

| | |
|---|---|
| Source | ATP match archive compiled by Jeff Sackmann, CC BY-NC-SA 4.0 |
| Mirror used | https://github.com/Aneeshers/tennis-sackmann-archive |
| Metric | Same ace-based scale as above |
| Coverage in this app | 685 calculated readings, 2012–2026, including 31 with published TA comparisons |
| Script | `tools/compute_speed.py` |

Every tour-level main-draw match with serve stats is read. For each player and season the ace
rate is computed on clay and on hard/grass, blended one third to two thirds, and each player's
rate of conceding aces while returning is recorded. For every match, the aces the server would
be expected to hit against that returner on a neutral surface come from the odds-ratio
combination of those two rates; the ratio of actual to expected aces is averaged across the
event, and the season is normalised so a tour-average event reads 1.00.

Where a published Tennis Abstract figure and a calibrated archive calculation both exist, the
calibrated calculation is the primary ranking value and the original published figure is retained
as `publishedSpeed`. There are currently 31 such event-season comparisons (27 in 2026 and
four in 2025). Where the archive has no calculation, the published value remains as a labelled
fallback. The two methods are different estimates; the TA value is retained for transparency,
not treated as ground truth.

## Fields in the dataset

```json
{
  "meta": { "generated": "2026-11-03", "season": 2026, "sources": [ ... ] },
  "tournaments": [
    { "id": "madrid", "name": "Madrid Masters", "city": "Madrid", "country": "ESP",
      "surface": "CLAY", "indoor": false, "level": "M1000", "altitudeM": 667 }
  ],
  "readings": [
    { "t": "madrid", "s": 2026, "cpi": 29.8, "src": "courtspeed" },
    { "t": "montpellier", "s": 2026, "speed": 1.26, "ace": 14.2, "matches": 27,
      "publishedSpeed": 1.49, "src": "computed" }
  ]
}
```

A tournament may hold separate CPI and Speed readings in one season. Where both Speed sources
cover the same event-season, the primary CALC record carries the original Tennis Abstract value
in `publishedSpeed`; this avoids duplicating the event-season row. `PaceData.value(id, season, metric)`
returns the live value first, then the calibrated calculation, then a published-only fallback.

## Derived values, and where they are computed

| Value | Where | Definition |
|---|---|---|
| Pace category | `PaceCategory.of` | ITF bands: ≤29 slow, 30–34 medium-slow, 35–39 medium, 40–44 medium-fast, 45+ fast |
| Speed band | `SpeedBand.of` | Our cut points on the ace-based scale: <0.75, <0.92, <1.08, <1.25, above |
| Change vs previous edition | `PaceAnalytics.ranking` | Against the most recent earlier season with a reading, skipping cancelled years |
| Is the move real | `PaceAnalytics.isMeaningful` | ±2.0 CPI points or ±0.05 speed — the ITF quotes ±2 points of uncertainty on its own method |
| Three-year average | `PaceAnalytics.threeYearAverage` | Mean of the readings inside a three-season window |
| Percentile | `PaceAnalytics.percentile` | Position within that season's field for that metric |
| Divergence | `PaceAnalytics.divergences` | CPI percentile minus speed percentile; |gap| ≥ 0.35 counts as a disagreement |

## Known gaps in the underlying data

- 2020 and parts of 2021 were cancelled, so those seasons simply have no readings.
- CPI history for the Grand Slams is thin before 2016.
- Roland Garros has no ace-based speed reading in the current 2026 list.
- Altitude is stored for a few venues only (Madrid 667 m, Gstaad 1050 m, Kitzbühel 762 m).
- The calibrated archive calculation covers event seasons from 2012 through 2026 where
  sufficient match statistics are available. Tennis Abstract is a rolling 52-week reference
  and remains the labelled fallback for event-seasons without an archive calculation.

## Regenerating

```bash
python3 tools/build_dataset.py
./gradlew :app:testDebugUnitTest
```

The script holds the two source tables verbatim and asserts that every reading points at a
declared tournament. The tests then re-check the generated file: unique ids, no orphan
readings, plausible ranges, no duplicate readings per event and season, and the expected
coverage counts. A typo therefore fails the build rather than showing up as a strange number
on screen.
